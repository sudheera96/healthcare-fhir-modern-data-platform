# HIPAA-Aligned Security Design

## Purpose

This document describes the security, privacy, and data-protection
practices considered for the Healthcare FHIR Modern Data Platform.

The platform uses synthetic healthcare data generated by Synthea and is
intended to demonstrate healthcare-oriented engineering practices.

> **Important:** This project is **HIPAA-aligned by design** for
> portfolio demonstration. It is not a HIPAA compliance certification,
> legal determination, or production PHI system.

## 1. Data Classification

The source is synthetic FHIR R4 healthcare data.

The platform is designed as though similar structures could contain
sensitive healthcare information in production.

For this implementation:

-   No real patient PHI is used.
-   Raw FHIR resources are retained only for engineering traceability.
-   Downstream analytical layers extract only fields required for the
    use case.
-   Sensitive identifiers are intentionally excluded from Silver and
    Gold analytical models.
-   Raw data is excluded from Git using `.gitignore`.

## 2. Data Minimization

The Bronze layer preserves the source FHIR representation.

The Silver layer extracts fields required for analytics, such as:

-   Patient identifier
-   Demographic attributes needed for analysis
-   Clinical conditions
-   Observations
-   Encounters
-   Dates and measurements

A synthetic SSN-like identifier was present in the FHIR Patient
resource. It was intentionally **not propagated into Silver or Gold**.

This creates the following pattern:

``` text
Raw FHIR
   |
   +-- SSN-like identifier
   |       |
   |       +--> Not propagated
   |
   +-- Required analytical fields
           |
           v
        Silver
           |
           v
          Gold
```

This is a data-minimization control rather than a claim that the source
itself contains no sensitive fields.

## 3. Access Control

The platform uses Databricks and Unity Catalog structures to organize
data assets.

A production deployment should implement:

-   Role-based access control
-   Least-privilege permissions
-   Separate development and production access
-   Restricted access to Bronze/raw data
-   Read-only analytical access where appropriate
-   Administrative access separated from analyst access
-   Service identities for automated workloads

Terraform is used to manage infrastructure configuration so changes can
be reviewed through Git.

## 4. Layered Data Access

The architecture separates:

``` text
Bronze
  ↓
Silver
  ↓
Gold
```

Bronze contains the most detailed source representation.

Silver contains standardized analytical structures.

Gold contains business-facing metrics and patient-level analytical
outputs.

This separation allows organizations to apply different permissions to
different data layers.

## 5. Sensitive Identifier Handling

The pipeline intentionally avoids propagating the synthetic SSN-like
identifier from the source Patient resource into analytical models.

The project therefore demonstrates a practical privacy principle:

> Do not expose sensitive identifiers to downstream consumers when those
> identifiers are not required for the analytical purpose.

Patient IDs used by the analytical models are synthetic identifiers from
the Synthea dataset.

## 6. Encryption

A production deployment should enforce:

-   Encryption at rest
-   Encryption in transit
-   Secure key management
-   Appropriate key rotation
-   TLS for service-to-service communication

This portfolio implementation relies on the underlying platform
capabilities and does not claim a customer-managed encryption-key
implementation.

## 7. Secrets Management

Credentials, tokens, passwords, and connection secrets must not be
committed to Git.

The repository excludes local environment artifacts and credentials
through `.gitignore`.

The local Databricks CLI uses platform authentication rather than
storing access tokens in source code.

Production deployments should use:

-   A secrets manager
-   Workload identity where supported
-   Short-lived credentials
-   Secret rotation
-   Environment-specific credentials

## 8. Auditability

The platform provides several layers of traceability:

-   Source-file metadata
-   Ingestion timestamps
-   Delta table history
-   Git history
-   GitHub Actions execution history
-   Terraform configuration history
-   dbt model/test execution history

A production healthcare deployment should additionally configure
centralized audit logging, access logging, and retention policies
appropriate to the organization's regulatory and contractual
requirements.

## 9. Data Quality as a Security and Reliability Control

Healthcare analytics should not silently accept malformed or incomplete
source data.

The platform uses a validation and quarantine pattern:

``` text
FHIR
  ↓
Bronze
  ↓
Silver
  ↓
Validation
  ├── PASS ──> Gold
  │
  └── FAIL ──> Quarantine
```

Encounter records without a valid patient reference are quarantined
rather than silently included in downstream patient analytics.

Current synthetic-data result:

-   71,751 total encounters
-   65,355 valid encounters
-   6,396 quarantined encounters
-   Approximately 8.9% quarantined

## 10. Production HIPAA Considerations

Before deploying a similar architecture with real PHI, the responsible
organization would need to evaluate and implement applicable
requirements, including:

-   HIPAA Privacy Rule
-   HIPAA Security Rule
-   HIPAA Breach Notification Rule
-   Administrative safeguards
-   Physical safeguards
-   Technical safeguards
-   Access control
-   Audit controls
-   Integrity controls
-   Transmission security
-   Risk analysis and risk management
-   Incident response
-   Business Associate Agreements where applicable
-   Workforce policies
-   Backup and disaster recovery
-   Retention and disposal requirements

The technology architecture alone does not establish HIPAA compliance.

## 11. Data Retention and Disposal

Production retention must be defined by the responsible organization
based on:

-   Applicable law
-   Organizational policy
-   Data-use agreements
-   Clinical requirements
-   Contractual obligations

This portfolio project does not establish a production retention period.

## 12. Security Position

Appropriate portfolio wording:

> "Healthcare analytics platform designed with HIPAA-aligned data
> minimization, access-control, auditability, and data-quality practices
> using synthetic FHIR data."

Avoid describing the project as:

> "HIPAA compliant"

or

> "HIPAA certified."

Formal compliance requires assessment of the complete technical,
administrative, physical, legal, and operational environment.
